# LibreScoot

⚠️ **WARNING: EXTREMELY EXPERIMENTAL - DO NOT USE ON REAL HARDWARE** ⚠️

This project aims to create a free and open source firmware for iMX6-based electric scooters. It is currently in early development stages and **might brick your scooter** if installed. This is a research project and should not be used on any real hardware yet.

## Requirements

- Any Linux distribution
- Python 3 + pip
- Docker

## Quick Start

[kas](https://kas.readthedocs.io/) manages Yocto layer repos and build configuration declaratively. `kas-container` wraps the build in a Docker container for isolation — consistent environment, no host contamination, shared sstate-cache for fast rebuilds.

```bash
# Install kas
pip3 install kas

git clone https://github.com/librescoot/librescoot.git
cd librescoot

# Build MDB firmware
kas-container build kas/mdb.yml

# Build DBC firmware
kas-container build kas/dbc.yml

# Build RPi4 development firmware
kas-container build kas/rpi4.yml

# Open a shell in the build environment
kas-container shell kas/mdb.yml
```

### Without Docker (native)

If you have all [Yocto build dependencies](https://docs.yoctoproject.org/ref-manual/system-requirements.html) installed, you can build natively:

```bash
kas build kas/mdb.yml
```

### Legacy Docker build (deprecated)

The old `build.sh` wrapper still works but is being phased out:

```bash
./build.sh mdb    # or: ./build.sh dbc
```

### Build Output

The compiled firmware will be located at:
```
yocto/build/tmp-glibc/deploy/images/unu-mdb/*.sdimg       # MDB
yocto/build/tmp/deploy/images/unu-dbc/*.sdimg              # DBC
yocto/build/tmp/deploy/images/librescoot-dbc-rpi4/*.sdimg  # RPi4
```

## Build Channels & Lockfile Workflow

LibreScoot uses a **channel-based release workflow** powered by [kas lockfiles](https://kas.readthedocs.io/):

```
nightly (AUTOREV) → testing (locked) → stable (locked + tagged)
```

### How channels work

| Channel   | Source            | Description |
|-----------|-------------------|-------------|
| **Nightly** | AUTOREV (latest)  | Builds from latest commits on all repos. May break. |
| **Testing** | Nightly lockfile  | Builds from a known-good nightly. More stable. |
| **Stable**  | Testing lockfile  | Promoted from testing after validation. Tagged as `vX.Y.Z`. |

### What is a lockfile?

A **kas lockfile** is a resolved configuration where every repository is pinned to an exact commit hash. It's generated by:

```bash
kas-container dump --lock kas/mdb.yml > kas/lock/nightly-mdb.lock.yml
```

Building from a lockfile guarantees identical output regardless of upstream changes:

```bash
kas-container build kas/lock/nightly-mdb.lock.yml
```

### Generating lockfiles manually

```bash
# Generate lockfiles for all targets
./kas/generate-lockfiles.sh nightly

# Generate for a specific target
./kas/generate-lockfiles.sh nightly mdb

# Promote nightly → testing
./kas/generate-lockfiles.sh testing

# Promote testing → stable (also tags the commit)
LIBRESCOOT_VERSION=v1.0.0 ./kas/generate-lockfiles.sh stable
```

### CI workflow

The GitHub Actions workflow (`build.yml`) automates this:

1. **Nightly** (cron 01:00 UTC): Builds with AUTOREV, generates lockfiles
2. **Testing** (manual dispatch): Builds from nightly lockfile, generates testing lockfile
3. **Stable** (tag push `v*`): Builds from testing lockfile, includes in release

## Build System Documentation

### kas Configuration

Build configuration lives in `kas/`:

```
kas/
├── base.yml      # Common settings: repos, layers, local.conf
├── mdb.yml       # MDB target (includes base.yml)
├── dbc.yml       # DBC target (includes base.yml)
├── rpi4.yml      # RPi4 dev target (includes base.yml)
├── generate-lockfiles.sh  # Helper to generate/promote lockfiles
└── lock/
    ├── README.md                  # Lockfile workflow docs
    ├── nightly-mdb.lock.yml      # Generated by CI
    ├── nightly-dbc.lock.yml
    └── ...
```

### Docker Isolation

`kas-container` uses Docker automatically — no custom Dockerfile or entrypoint needed. It handles volume mounts, user mapping, and environment setup. The sstate-cache and downloads directories persist between builds for speed.

Under the hood, it pulls the official kas Docker image matching your kas version and runs the build inside it. Nothing to configure.

### Target Differences

#### MDB (Middle Driver Board)
- Based on iMX6 platform
- Uses Linux kernel 5.4.24
- Default configuration in meta-librescoot

#### DBC (Dashboard Controller Board)
- Based on iMX6 platform
- Uses newer Linux kernel 6.6.3
- Additional layers for multimedia and UI support

#### RPi4 (Raspberry Pi 4 - Development)
- ARM64 platform for development/testing
- Runs the DBC image on commodity hardware
- Uses meta-raspberrypi layer

## Flashing Instructions

To flash firmware:

1. Connect the board via USB
2. Ensure the board is in mass-storage mode
3. Flash:
```bash
gunzip -c *.sdimg.gz | sudo dd of=/dev/sdX bs=4M oflag=direct status=progress
```
Replace `/dev/sdX` with your actual device path.

For MDB: Connect via mini-USB, power with a stable 12V supply.
